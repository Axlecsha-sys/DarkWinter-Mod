# DV-006: подготовка очереди загрузки чанков

Первый адресный этап устраняет повторную сортировку footprint в TestingImportLoader.prepareChunks. Общий планировщик фоновых задач Minecraft этим изменением не заменяется.

## Подтверждённый источник

Импорт, операции редактора и Undo/Redo используют общий native chunk lease. До изменения каждый опрос заново создавал ArrayList и сортировал весь набор координат по x, затем z, хотя набор владельца уже зафиксирован и изменение footprint запрещено.

Native профиль операции на 4096 чанках подтвердил повторение: в основном before-прогоне было 934 вызова и 934 сортировки. JFR содержит стеки TimSort/компараторов и места выделения ArrayList, копирования массива и рабочих массивов сортировки внутри настоящего prepareChunks. Sampled allocation weights определяют источник, а не точное число всех объектов.

## Изменение

После проверки общего лимита новый Owner один раз получает отсортированный неизменяемый List. Последующие опросы используют этот порядок. Начало timeout фиксируется перед первоначальной сортировкой. При освобождении владельца освобождается и ссылка на его список.

Сохранены серверная authority, проверка входного набора на каждом вызове, запрет изменения footprint, timeout 180 секунд, предел 4096 различных чанков для объединения владельцев, общий лимит восьми новых запросов за тик и восьми незавершённых загрузок. Проверка FULL и загрузки сущностей, совместные tickets и release/cancel не изменены. Упорядочивание остаётся signed x, затем signed z.

Новый список хранит до 4096 ссылок на владельца. Совпадающие footprint разных владельцев могут хранить отдельные списки; глобальный лимит памяти всех владельцев не вводится. Повторные Set.copyOf, validation, проверки futures/readiness и обходы O(N) остаются.

## Native before/after

Minecraft 26.3 / Fabric / Java 25, обычный клиент Loom с интегрированным сервером, OpenGL / RX 7600 XT. Для каждой версии использована отдельная копия одного flat save, фиксированная камера и одинаковый диапазон чанков x/z 128–191. Модули и F10 выключены, сервер не заморожен, native 20 TPS. SDK/GameTest scheduling hooks не используются.

Загрузка 4096 чанков проверяет реальный порядок запросов и lifecycle. Её длительность зависит также от генерации и диска, поэтому суммарное время этой фазы не используется для вывода об ускорении очереди.

После готовности та же операция с удерживаемыми 4096 tickets проходит отдельные 64 последовательных native server ticks. Все вызовы возвращают ready=true; новых native запросов нет. Этот контроль отделяет повторную подготовку от переменной стоимости поступления новых чанков.

| Наблюдение в контрольной фазе | До | После |
| --- | ---: | ---: |
| Опросы / новые запросы | 64 / 0 | 64 / 0 |
| Вызовы List.sort | 64 | 0 |
| Приблизительные выделения на вызов, среднее | 262 024,875 B | 213 450,625 B |
| Приблизительные выделения за 64 вызова | 16 769 592 B | 13 660 840 B |
| Среднее wall time всего prepareChunks | 2,557 мс | 1,596 мс |
| Медиана wall time всего prepareChunks | 2,526 мс | 1,626 мс |

В этом контроле наблюдаемая разница счётчика выделений уменьшилась на 18,5%, среднее время метода — на 37,6%. Повторный неизменённый before-прогон дал 2,530 мс и 262 054 B на вызов. Это ограниченное сравнение метода, а не распределение FPS/TPS всей игры или изолированный таймер сортировки.

JDK ThreadAllocatedBytes является приблизительным счётчиком потока; это не занятый heap и не точное число объектов. Счётчики охватывают весь настоящий метод и небольшие одинаковые primitive hook writes. Создание JFR-события и экспорт происходят после измеренного delta. JVM flags, GC и настройки памяти не менялись, явный GC не вызывался.

JFR содержит все 998 измеренных вызовов before и 1009 after, включая контрольные 64; поля custom events совпадают с JSON, DataLoss отсутствует. В after sampled стеки повторной сортировки не зарегистрированы; однократная начальная сортировка подтверждается точным hook-счётчиком, а не отсутствием samples.

## Проверки поведения

В фазе загрузки before/after принято ровно 4096 уникальных запросов с одинаковым SHA-256 порядка cbbcb416dae86580503b6a0078d6bcd904c7533a76927f743ca778cd77b7cb43. Максимум — восемь за один тик, peak in-flight — восемь. After: 945 опросов и одна сортировка. Все чанки достигли FULL и готовности сущностей. До release удерживались 4096 настоящих tickets; после — ноль и удалённый Pool. Положение игрока не менялось.

На исправленной версии после остановки профиля прошли семь групп проверок настоящих production API и native ticket storage:

- отклонение null server и вызова вне server thread до admission;
- неверные tokens, null/size/bounds, пустой footprint без создания lease;
- произвольный порядок и дубликаты прежнего набора, отклонение изменения набора и независимость от изменяемой входной коллекции;
- два владельца и повторные опросы в один native tick — общий предел восьми запросов;
- перекрывающиеся владельцы, предел объединения и точное сохранение общих tickets при частичном release;
- реальные ветви отказа failed future и timeout через изолированную временную подстановку состояния собственного Pool;
- cancel всех leases, отсутствие tickets/Pool и сохранение metadata и режима симуляции.

Functional baseline явно NOT_RUN. При cancel все три наблюдаемых futures уже завершились (pendingAtCancel=0): поведение действительно незавершённого future этим сценарием не доказано. Published-host managed scope и dedicated-server authority отдельными online/server стендами не проверялись. В raw report фраза allocation-free для empty неточна: доказано отсутствие lease, измерения выделений для empty не было; пояснение приватного стенда исправлено.
