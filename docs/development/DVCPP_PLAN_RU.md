# DVCPP: кандидаты на C++ и порядок проверки

Восемь направлений для Minecraft 26.3 / Fabric / Java 25. Номера DVCPP-001–DVCPP-007 закреплены по исходному перечню; DVCPP-008 добавлен для численных пакетов редактора и тестового острова. Место в очереди может изменяться по измерениям. Это отдельная программа экспериментов, связанная с [DV](DV_FIXES_RU.md). Перенос языка сам по себе не закрывает соответствующий DV.

Приоритет — больше FPS и ровнее время кадров, включая редкие задержки. Допустимы осознанные визуальные компромиссы: иной способ затенения, меньше деталей вдали или более дешёвые эффекты, если результат остаётся цельным, красивым и стабильным при движении. Каждый такой вариант сравнивается на одинаковой камере и маршруте; швы, мерцание и резкие переходы качества не считаются приемлемой ценой. Это разрешение менять изображение, а не игровые правила, сохранённый мир или порядок серверных событий.

P0 — обязательные измерения и корректность перед любым переносом. P1 — ближайшие кандидаты. P2 — после подтверждения стоимости и подходящей границы данных. P3 — поздний этап с высокой стоимостью интеграции. Номер означает направление, а не завершённое исправление.

## P0: условия для каждого направления

Сравниваются три варианта: текущий путь, улучшенная Java с тем же алгоритмом и компактными данными, C++ с полными расходами интеграции. Отдельный kernel benchmark используется только для диагностики.

В отчёте учитываются получение согласованного снимка, подготовка пакета, копии/переход FFM, native работа, чтение/запись результата, его публикация и применение. Разделяются wall time, CPU, работа фоновых потоков, ожидания и время кадра. Время worker нельзя напрямую пересчитать в FPS. Проверка результата и хеширование отмечаются отдельно и одинаково исключаются из сравниваемого timed span.

Фиксируются hash фактически загруженной DLL и production source identity, ABI, toolchain/flags, Java/GC/heap, backend, режим эксперимента, настройки, seed/исходная копия мира и прогрев. Исходник C++ в sourceHash не доказывает соответствие отдельно загруженной DLL. Во всех измеренных C++-проходах должны быть реальные native-вызовы без незаявленного Java fallback; fallback остаётся отдельным функциональным испытанием.

Два обязательных сценария — одинаковый маршрут по заранее созданной территории и новые области на одинаковых исходных копиях мира. Порядок A/B чередуется, выполняются повторы. Публикуются сырые времена, p95/p99/редкие максимумы, задержка появления/применения чанков, очереди, native/heap memory и паузы GC. Отсутствие ухудшений проверяется и в уже загруженной спокойной сцене.

Сокращение времени полного пути должно воспроизводиться и превышать разброс измерений; универсальный процент ускорения заранее не задаётся. Повторяемое ухудшение, нарушения результата или рост памяти блокируют включение по умолчанию.

Java/Fabric сохраняет владение миром, Mixin/event интеграцию и применение результатов. C++ получает ограниченные массивы/снимки для законченной операции, без обратного вызова Java для каждого блока и без доступа к изменяемому миру из произвольного потока. Графические команды остаются в существующей абстракции Minecraft. Указатели не переживают владельца/резервирование буфера; отмена, disconnect/reload и worker lifetime проверяются отдельно.

Обычный путь сохраняется для неподдержанных данных, отсутствующей библиотеки и обнаруженных ошибок. Fallback не гарантирует восстановление после повреждения native памяти. Перед распространением нужны сборки для заявленных ОС/архитектур, контролируемая загрузка артефакта, проверки границ, конкурентности и native sanitizers/fuzz. Пока реально проверена Windows x64, DLL отдельно и отсутствует в mod JAR.

## DVCPP-001: геометрия чанков

Ближайший шаг — найти выигрыш алгоритма и границы пакета в реальном SectionCompiler, а не автоматически включить текущий CPP_PACKED. Маски 18³ и финальная запись вершин — разные эксперименты; их выгоды не складываются без измерения совместного полного пути.

Следующий kernel находится до финального writer: массовое определение граней и расчёт AO/соседнего света для явно подходящих простых блоков. В фактическом BlockModelLighter подготовка одной грани многократно читает соседние состояния, свет, shade и проницаемость. Пакет должен использовать уже согласованный section/halo и компактные признаки материалов; Java сохраняет модельные callbacks и обработку сложных случаев. Повторный сбор object-состояний для каждой грани может уничтожить выгоду native-цикла и входит в полный замер.

Кандидат получает свет, tint и шаблоны материалов один раз на ограниченный пакет, а не вызывает Java для каждого блока или quad. Возможность объединения поверхностей рассматривается отдельно: нужны совместимость UV/материала, tint, света/AO и затенения, а не только одинаковый тип блока. Для заранее запечённых meshes DarkWinter перенос bake не заменяет оптимизацию повторного AO/emit пути при сборке секции.

Готовность: реальные непустые секции используют результат C++; полный compile и задержка появления геометрии улучшаются в повторах. Для текущего пакетного writer требуется совпадение всех vertex/index bytes, draw state, visibility и block entities. Для будущего изменения топологии нужна отдельно определённая проверка эквивалентной поверхности, материалов/света и визуальных стыков, а не ложное требование одинакового числа вершин.

Обязательны границы/углы секций, правки игрока, empty→solid→empty, отмена/reuse, reload, плиты/ступени, листва, стекло, вода, эмиссия и AO, Vulkan и OIT on/off. Последующие OpenGL-прогоны исключены из активной матрицы. Существующие Pipeline Guard, native GPU upload и renderer fallback сохраняются.

Опорный [аудит](CPP_AUDIT_RU.md): native-выполнение и byte parity подтверждены на выбранных секциях; устойчивое ускорение всего сборщика пока не установлено. [Текущий эксперимент](CPP_CHUNK_MESH_RU.md) и [маски](CPP_VOXEL_FACES_RU.md) не являются завершением DVCPP-001.

## DVCPP-002: математика генерации

Сначала разделить стоимость density/noise, зависимостей соседних чанков, ожиданий, света, хранения и доставки. Переносить только подтверждённо дорогое численное ядро крупным пакетом. Планировщик генерации и применение блоков остаются у игры.

В 26.3 шумы и функции плотности вычисляются с одинарной точностью, включая промежуточные шаги. Поэтому нужны правила именно этой версии для float, seed/RNG, порядка операций и округлений; fast-math/FMA не допускаются без отдельного доказательства эквивалентности. Это подтверждено [официальными изменениями 26.3](https://www.minecraft.net/en-us/article/minecraft-java-edition-26-3).

Фактическая пакетная граница уже существует: DensitySampler.sampleVolume заполняет DensityBuffer с float[], а NoiseBasedChunkGenerator.doFill получает volume до применения BlockState. Текущие PerlinNoise/GradientNoise и sampler context проверяются по локальному 26.3 source; старый ImprovedNoise или форматы генератора предыдущих версий не подставляются.

Проверенный пример — [C2ME, MixinPerlinNoiseSampler, commit 65fe39997e1b531119104dfe42ca99329ede57f8](https://github.com/RelativityMC/C2ME-fabric/blob/65fe39997e1b531119104dfe42ca99329ede57f8/c2me-opts-natives-math/src/main/java/com/ishland/c2me/opts/natives_math/mixin/MixinPerlinNoiseSampler.java) из ветки dev/26.3.0: целый SamplingRegion передаётся native-функции, небольшие объёмы оставляются Java. Это пример организации пакета, не сторонняя игровая зависимость и не доказательство скорости или эквивалентности будущего порта DarkWinter. При использовании чужого кода сохраняются его лицензионные уведомления; у проверенного файла MIT header.

Heap-backed FFM и critical(true) из внешнего проекта не копируются автоматически. [Контракт Java 25](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/foreign/Linker.Option.html) ограничивает critical короткими вызовами; долгий native-пакет требует обычного downcall и собственного протокола памяти. Копирование float-массивов и преобразование sampler graph учитываются вместе с вычислением.

Готовность: одинаковые численные результаты и итоговый мир на наборе seed/координат, отрицательных и далёких координатах, границах чанков, структурах и поддержанных datapacks. Сравниваются блоки, биомы, heightmaps и стыки; unsupported graph использует прежний путь. Измеряется полный путь генерации/появления новых чанков. Маршрут по уже созданной территории не считается доказательством ускорения генератора.

## DVCPP-003: видимость

Сначала измерить existing visibility graph/frustum/object checks, убрать повторные проверки и проверить организацию данных. C++ рассматривается для больших пакетов компактных объёмов, а не одиночных проверок расстояния. В фактическом 26.3 SectionOcclusionGraph уже строит полный граф в background executor по копиям loaded/empty sets, а Frustum использует JOML. Обещать выигрыш только от переноса в другой поток или язык нельзя; упаковка AABB и публикация bitset должны окупаться полным путём.

Готовность: сохранены консервативность отсечения, попадание необходимых объектов в кадр и отсутствие popping на поворотах, телепортах, изменениях чанков и камеры. Стоимость подготовки пакета, вычисления и применения результата меньше Java. Не вводится блокирующее GPU readback ради CPU-отсечения.

## DVCPP-005: данные чанков

Проверять только оставшийся дорогой пакетный bit/palette/buffer участок после DV-019. У однородной палитры уже убрана лишняя работа; переписывание её заново не считается новым выигрышем. Формат мира, codec, порядок пакетов/ACK, atomic saves и барьеры native журнала сохраняются.

Готовность: PackedData/codec/NBT/binary roundtrip, mixed и расширявшиеся палитры, block entities, полный save/reopen и обработка повреждённого входа дают прежний результат. Измеряются полная загрузка/сохранение или подготовка данных, выделения и задержки, не только побитовый цикл.

Сжатие рассматривается лишь после профиля фактической реализации: стандартный Java Deflater уже использует ZLIB, что указано в [Java 25 API](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/zip/Deflater.html). Ещё одна обёртка над компрессором сама по себе не является переносом полезной работы.

## DVCPP-004: свет

Сначала измерить стоимость существующих очередей и повторных обновлений. Возможная граница C++ — массивы sky/block light, ограниченный пакет распространения/удаления и явные обмены на границах. Thread ownership и жизненный цикл чанков остаются согласованными с сервером; перенос на GPU не заменяет серверные значения света.

Готовность: одинаковые light arrays после установки/удаления источника и непрозрачного блока, перекрытия skylight, изменений на границе/углу, unload/reload и конкурирующих изменений. Проверяются стабильное завершение очередей, отсутствие потерянных обновлений и совпадение окончательного mesh lighting.

## DVCPP-006: ресурсы

Сначала разделить уже нативное декодирование, IO, операции над пикселями/mipmaps, model bake и атласы. Кандидат — дорогая пакетная CPU-обработка с ясными входами; решение не сводится к дублированию существующего декодера.

Готовность: меньшее полное время запуска/reload с прежними пикселями, mipmaps, прозрачностью, цветовым пространством, UV/моделями и atlas packing на поддержанных packs. Проверяются invalid inputs, отмена, повторная reload и освобождение памяти. Прирост обычного FPS не заявляется, если стадия не выполняется в проблемных игровых кадрах.

## DVCPP-007: путь и коллизии

Два отдельных подэтапа: пакетный поиск маршрутов по согласованному снимку и пакетные геометрические проверки. Полный перенос AI/сущностей не входит в направление.

Готовность: актуальная инвалидизация снимка, прежние правила проходимости и достижимости, стоимость путей и согласованный выбор равных кандидатов; отдельно формы/границы collision, поршни, ступени и движение. Сервер применяет только проверенный актуальный результат. Упрощение поведения удалённых мобов или изменение частоты AI не выдаётся за эквивалентную C++-оптимизацию.

## DVCPP-008: численные пакеты редактора и тестового острова

Цель — уменьшить задержки крупных brush/resize/пересоздания острова, а не объявить постоянный прирост FPS. TestingIslandGenerator.surfaceHeight содержит atan2/hypot/sin/cos/pow; TestingTerrain.height/naturalState и smooth-кисть могут повторно вычислять одни и те же столбцы. Сначала улучшенная Java рассчитывает высоты и естественные маски один раз на столбец и переиспользует результат.

Если после этого численная часть остаётся дорогой, C++ получает неизменяемую конфигурацию, координатный прямоугольник и ограниченные массивы высот/масок защиты. Возвращаются только target heights/material IDs. BlockState, provenance, проверка protected zones, порядок применения, Undo/Redo, REDO-журнал и атомарное сохранение остаются у существующего Java transaction engine. Native-функция не читает живой мир и не изменяет его напрямую.

Готовность: одинаковые значения и конечные изменения для всех форм острова, seed, отрицательных координат, границ и brushes; сохранены защищённые/авторские объекты, отказ и отмена без частичного применения. Измеряется вся операция, включая снимок и применение, а также время серверного тика и отклик редактора. Новых замеров и реализации пока нет.

## Границы программы и источники

UI, инвентарь, предметы, события и обычная игровая логика остаются в Java, пока профиль не выделит конкретную тяжёлую операцию. Независимая симуляция, региональные тики, замена GPU backend и полный перенос движка не входят в эти восемь кандидатов. Дальний LOD — отдельное изменение визуального представления с собственными данными, переходами и проверкой, а не готовая функция текущего native writer.

Стоимость OIT, прозрачности воды, объёмного света, тумана и полноэкранных post passes относится прежде всего к GPU-проходам. Если ограничение находится там, перенос Java-подготовки на C++ не заменяет оптимизацию GLSL, числа выборок, промежуточного разрешения и порядка проходов. Более дешёвое изображение может быть осознанным режимом качества, но его выигрыш и внешний вид проверяются отдельно. Контролируемые Vulkan-прогоны подтвердили рост времени GPU над водой при OIT; упрощённый вариант оставлен экспериментом из-за ранней глобальной инициализации и ограниченного выигрыша. [Измерения, исправления выделений и ограничения](DV_014_RU.md).

В 26.3 уже есть terrain MultiDrawIndirect на поддержанных устройствах и OIT в Improved Transparency; добавлять их повторно под видом C++-оптимизации не требуется. Источник: [Minecraft 26.3](https://www.minecraft.net/en-us/article/minecraft-java-edition-26-3). Модели содержат UV, cullface, rotation, tint и shade; универсальность алгоритма простого куба из них не следует: [Fabric Block Models](https://docs.fabricmc.net/develop/blocks/block-models). Открытая страница Fabric сейчас помечена 26.2; точные интеграционные контракты 26.3 проверяются по фактическим исходникам проекта.

Текущий FFM-мост сохраняется для сравнения; переход на JNI сам по себе не цель. Все результаты готовности относятся к конкретной библиотеке, версии игры и проверенной платформе. План не означает запуска новых реализаций или включения текущего C++ режима по умолчанию.
