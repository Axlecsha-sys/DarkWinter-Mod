# Эксперимент: Java 25 против C++ (видимые грани секции)

## Актуальный этап: реальная запись геометрии

Новый эксперимент `/dwmesh` описан в [CPP_CHUNK_MESH_RU.md](CPP_CHUNK_MESH_RU.md): штатный Minecraft/Fabric, пакетный Java и C++ записывают настоящие вершинные буферы секций. Сравнение `/dwmesh compare 4` повторно собирает один и тот же снимок секции и проверяет выходные байты. Генератор мира, световая симуляция и GPU API не заменяются. По умолчанию выбран VANILLA.

Ниже сохранена история **предыдущего** эксперимента `/dwvoxel` с масками граней. Его самостоятельный `voxelFacesBenchmark` не подключён к игре сам по себе; клиентский адаптер описан отдельно ниже. Он не является новым пакетным сборщиком. Не включайте оба эксперимента одновременно: `/dwmesh mode ...` отключает старый проход масок.

Исходный standalone-тест работает на сетке 16×16×16 и вычисляет только 6-битные маски видимых граней непрозрачных единичных кубов, а не полную геометрию.

## Формат данных

- Вход: 18×18×18 байт с одноячейковой границей, 0 — воздух, 1 — полный непрозрачный куб; другие виды блоков не моделируются.
- Индекс входа: `((y * 18 + z) * 18 + x)`, центральные координаты от 1 до 16.
- Выход: 4096 байт для центральных 16×16×16, индекс `((y * 16 + z) * 16 + x)`, координаты от 0 до 15.
- Биты: `-X=1, +X=2, -Y=4, +Y=8, -Z=16, +Z=32`. Если текущая ячейка заполнена, бит выставлен только при воздухе в соседней ячейке.
- Возвращается общее количество открытых граней; при некорректных размерах или указателях C-функция возвращает отрицательный код.

## Состав

- `java/VoxelFacesExperiment.java` — эталон Java, FFM-мост, тесты корректности и самостоятельный бенчмарк.
- `native/voxel_faces.cpp` и `native/CMakeLists.txt` — нативная C ABI-функция, без Minecraft-зависимостей.
- `gradle/voxel-faces.gradle` в корне репозитория — отдельные Gradle-задачи. DLL и standalone-тесты остаются в `build/voxel-faces/`, в JAR мода не включаются. Клиентские адаптеры из `src/client` включаются в мод, но по умолчанию отключены.

## Запуск из корня проекта

```powershell
.\gradlew.bat voxelFacesEnvironment
.\gradlew.bat voxelFacesToolchains
.\gradlew.bat voxelFacesFallback
.\gradlew.bat voxelFacesJavaBenchmark
# Windows: при первом запуске загрузится проверенный переносимый Zig/Clang 0.14.1:
.\gradlew.bat voxelFacesBootstrapCpp
.\gradlew.bat voxelFacesVerify
.\gradlew.bat voxelFacesBenchmark
```

Для Java-проверок нужен JDK 25. На Windows x64 отдельные системные CMake и Visual Studio Build Tools **не требуются**: при первом запуске `voxelFacesBootstrapCpp` Gradle скачивает с официального сайта архив Zig 0.14.1 (82 229 343 Б), сверяет строгий SHA-256 `554f5378228923ffd558eac35e21af020c73789d87afeabf4bfd16f2e6feed2c` и распаковывает переносимый C++/Clang в `build/voxel-faces/toolchains/`. Права администратора и системный PATH не меняются. DLL создаётся в `build/voxel-faces/bin/`. На Linux/macOS сохраняется путь CMake и C++17-компилятор (через `DW_CMAKE_EXECUTABLE`). Java запускается с `--enable-native-access=ALL-UNNAMED`. Путь DLL передаётся непосредственно программе. Вне `develop/с++` и `develop/c++` экспериментальные задачи откажутся работать.

## Что считается результатом

1. Сравнение с независимым наивным алгоритмом на фиксированных и псевдослучайных сценах, проверка всех масок и количества граней.
2. Результат Java и C++ должен совпасть побайтово. Отсутствие библиотеки не должно ломать Java fallback, но задача `voxelFacesVerify` требует успешного запуска C++.
3. Отдельно выводятся времена полного Java-пути и полного C++ пути **включая копирование в/из native memory**, а также C++ FFM-вызова с заранее загруженными массивами (это не чистое время C++-ядра). Среднее FPS Minecraft из этих чисел выводить нельзя.
4. Обычная сборка `build` не требует CMake/C++ и не упаковывает DLL или standalone-бенчмарки в игровой JAR. Код клиентских переключателей и адаптеров включается в JAR с выключенным экспериментом по умолчанию.

## Текущее состояние проверок

- Windows / Java 25: `voxelFacesFallback` — PASS, 264 сцены; Java-only benchmark — 8,72 мкс/секцию в отдельном предварительном прогоне.
- Windows / Zig 0.14.1: официальный архив скачан и проверен, компилятор запущен; `dw_voxel_faces.dll` собрана, `voxelFacesVerify` — PASS на 264 сценах, через настоящий FFM downcall; проверены некорректные размеры/NULL.
- Windows / Java + C++: `voxelFacesBenchmark` — три успешных самостоятельных прогона, каждый 48 сцен × 150 проходов × 7 повторов. Медианы (мкс/секцию): Java 9,00 / 8,78 / 8,80; C++ + FFM + копирование 8,56 / 8,40 / 8,36; C++ + FFM на предзагруженных входах 8,38 / 8,20 / 8,26. Выигрыш полного C++-пути по времени относительно Java около 4,3–5,0% в этих запусках, без заявлений о FPS. CMake/MSVC не устанавливались: использован переносимый Zig/Clang.
- Независимая Linux-среда: точный SHA-256 C++ исходника проверен, сборки g++ и clang++ PASS; 264 сцены и проверки ошибочных размеров/NULL PASS на g++/clang++ (эти проверки не заменяют Windows/FFM).
- Обычные `compileJava`, `compileClientJava`, `visualsDoctor` — PASS; нативный эксперимент отсутствует в исходниках модовых source sets.

## Реальное экспериментальное подключение Minecraft 26.3

Client-only (ветка develop/с++): три Mixin-перехвата оборачивают штатный `SectionCompiler.compile` и оптимизируют только отрицательное решение `Block.shouldRenderFace` для восьми ванильных блоков с шестью полными окклюзионными гранями: stone, dirt, cobblestone, deepslate, granite, diorite, andesite, bedrock. Проверка геометрии блоков, создание quads, подсветка/AO, материалы, translucency, шейдеры, fluid meshes и синхронизация очереди остались у Minecraft / Fabric Indigo. Все остальные состояния без изменения продолжают обычный путь. Склейки самих кубов, буферизации GPU и замены рендерера здесь **нет**.

Клиентское управление (после `.\\gradlew.bat runClient`):

- `/dwvoxel status` — выбранный/фактический режим, DLL, число обработанных секций, пропущенных проверок, время подготовки снимка и FFM, ошибки проверки;
- `/dwvoxel mode java` — обычный рендерер Minecraft (по умолчанию);
- `/dwvoxel mode cpp` — экспериментальная маска C++ из DLL с полной Java подготовкой данных и Java fallback при ошибке;
- `/dwvoxel mode auto` — синтетическая локальная калибровка; требует превосходства native полного пути примерно на 15%, иначе Java (это **не** автоматический анализ реальных FPS);
- `/dwvoxel rebuild` — запрашивает штатную полную пересборку видимых чанков, которая нужна после смены режима;
- `/dwvoxel capture 20` — запускает DV-032 на 20 секунд и после закрытия чата через ~1 секунду инициирует одну полную пересборку, сохраняя отчёт в `run/performance-reports/` (команда во время другой записи отказывается запускаться).

Режим хранится в `run/config/darkwinter/voxel-experiment.properties`. `runClient` получает только dev JVM flag `--enable-native-access=ALL-UNNAMED` и путь DLL под `build/voxel-faces/bin/`; C++ бинарник **не включён** в распространяемый JAR. Отсутствующая DLL или запрет native access оставляют Java путь. Фактический путь CPP подтвердился в уже существующем лабораторном мире: 205 sections, 2 762 398 пропущенных проверок граней, 0 несовпадений в проверенных выборках, средняя полная Java подготовка + вызов 2792 мкс на секцию и сама FFM+копирование 47 мкс на секцию. **Подготовка дороже нативного вызова в десятки раз, так что реальный выигрыш по FPS не доказан и возможна регрессия.** После этого прогона подготовка дополнительно изменена: добавлены палитровый `maybeHas` для отказа от пустых кандидатов, чтение центра напрямую из immutable `PalettedContainer` и пропуск неиспользуемых диагональных ячеек halo. Новая версия успешно скомпилирована, однако этот дополнительный шаг ещё **не проверен в игровом мире и не измерен**. Синтетический microbenchmark Java/C++ выше не должен выдаваться за измерение FPS.

Для сравнения: в одном и том же мире и с неподвижной камерой выполнить `/dwvoxel mode java`, затем `/dwvoxel capture 20`, дождаться завершения записи и фоновой пересборки. Затем `/dwvoxel mode cpp` и `/dwvoxel capture 20` при тех же графических настройках. Рекомендуются несколько чередующихся записей, период прогрева и отдельная проверка картинки. Режим записывается в `configHash` и metadata DV-032, поэтому JSON разных режимов **намеренно не имеет одинакового configHash**; `sceneHash=unverified` также не позволяет объявить результаты строго сопоставимыми. Сравнивать по одинаковому экспериментальному сценарию, сообщая эту оговорку. По окончании вернуть `/dwvoxel mode java`.

Ограничения: standalone-алгоритм генерирует только маски граней, а не настоящие render sections с освещением, материалами, прозрачностью, анимацией, различными формами блоков или GPU-upload. Реальный клиент использует его только как необязательный дорогой предварительный pass, а штатный рендерер строит геометрию как раньше. Для окончательного вывода необходимы одинаковые профили и измерение стоимости подготовки snapshot, а не только вызова C++.
