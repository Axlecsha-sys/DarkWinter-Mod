# DV-017: ограничение приоритетных перестроений секций

## Причина и изменение

В Minecraft 26.3 LevelRenderer.compileSections обходит подготовленные SectionUpdateRenderState. NEARBY и PLAYER_AFFECTED могут направить несколько секций подряд в compileSync на render thread; общего бюджета серии нет. Неприоритетные секции уже используют native worker queue. Vanilla default — NONE.

SectionCompileBudget принадлежит экземпляру LevelRenderer. При каждом compileSections устанавливается свежий монотонный timestamp. Первая приоритетная секция остаётся синхронной. Следующая допускается только до истечения 2 мс и до достижения лимита двух секций. Остаток сразу передаётся штатному compileAsync с тем же извлечённым RenderSectionRegion. Порядок выбора секций остаётся нативным: первая секция не обязательно соответствует последнему действию игрока.

Секции не пропускаются и не читаются заново из изменяемого мира. Сохраняются native snapshots, очередь, buffer pool, staging/upload и visibility. NONE и неприоритетные секции остаются фоновыми. При нескольких player-changed секциях часть геометрии теперь появляется после фоновой сборки. Одиночный приоритетный rebuild проверяется отдельно.

Бюджет мягкий: неделимый compileSync может сам занять больше 2 мс. Это ограничение серии дополнительных задач, а не обещание максимального времени всего кадра.

## Отмена пустого результата

При проверке жизненного цикла воспроизведена отдельная ошибка исходной 26.3: EMPTY-ветка CompileTask.doTask публикует результат без повторной проверки отмены. Старый worker может затереть новый готовый mesh и освободить его GPU allocations.

CancelledEmptySectionMixin сериализует cancel и проверку с EMPTY-публикацией одним monitor конкретной задачи. Monitor освобождается до native copyLock и освобождения буферов; ни meshing, ни ожидание GPU под ним не выполняются. При отмене native cleanup получает безопасный EMPTY sentinel вместо нового живого mesh, а результат задачи становится CANCELLED.

Это защита EMPTY и block-entity-only ветки без rendered layers. Она не объявляется универсальной защитой всех nonempty upload callbacks. Остальные вопросы инкрементальных meshes и их версий остаются в DV-011.

## Проверка

- runDv017BudgetTest: PASS, границы времени и количества, reset, отрицательный nanoTime и его переполнение; миллион прогретых вызовов — 0 выделенных байт по ThreadMXBean.
- Финальный OpenGL клиент: PASS, 18 измерительных фаз, 16 lifecycle checks, Mixin audit.
- Финальный Vulkan клиент: PASS, те же 18 фаз и 16 lifecycle checks.
- По две пары кадров с OIT OFF/ON на backend: средняя абсолютная RGB-разница 0.
- NONE и unmarked PLAYER_AFFECTED сохраняют нулевое число sync вызовов. Marked burst достигает 1 sync + 8 async в измеренной тяжёлой сцене.
- Сравниваются актуальные mesh identities/task timestamps и загруженные vertex/index GPU slices. Пустота очереди не используется как доказательство завершения.
- Lifecycle покрывает solid → air → solid, реальную отмену EMPTY, переиспользование секций камерой, resource reload прозрачного блока, одиночные player-marked изменения в центре и углу секции.
- Center/corner проверки подтвердили native synchronous compile до и после. Наблюдение server mutation → packet delivery → upload занимает около 150 мс в пошаговом SDK-сценарии в обоих вариантах; это не измерение задержки мыши и не обещание сетевой задержки.
- Исходный canceled EMPTY repro дал FAIL до защиты в обоих режимах выбора задач. После защиты — PASS: отменённый EMPTY не опубликован, новый STONE mesh остаётся виден.
- Чистая публикационная сборка проверяется без private tools/tests.

## Измерения тяжёлой серии

Windows, Ryzen 5 8400F, Radeon RX 7600 XT, Java 25; обычный загруженный мир, 1280×720, render distance 8, FOV 110, VSync OFF, framerate setting 260 (unlimited). Симуляция заморожена. Восемь чередующихся before/after bursts содержат по девять готовых непустых секций.

Before отменяет только budget decision в private test mod и воспроизводит исходный неограниченный sync выбор. EMPTY guard включён в обоих финальных timing-вариантах; его исходный repro сохранён отдельно. Production не содержит тестовых flags.

| Backend | Compile phase до, мс | После, мс | Самый длинный кадр каждой серии до, мс | После, мс |
| --- | --- | --- | --- | --- |
| OpenGL | 74.76–90.66 | 8.15–9.01 | 78.32–97.91 | 9.60–10.91 |
| Vulkan | 72.66–81.69 | 7.95–8.80 | 75.88–87.93 | 9.68–11.41 |

После правки весь mesh в этой сцене наблюдается готовым примерно через 49–50 мс от mark против 76–95 мс до неё. Проверка готовности выполняется SDK с дискретностью примерно 20 Hz; это верхняя граница первого наблюдения, не точный аппаратный момент публикации.

Сохранены все frame intervals, p50/p95/p99/max и реальные sync/async spans. В короткой фазе единственный hitch может составлять меньше 1% кадров, поэтому p99 не всегда включает его; итоговый вывод основан также на первом затронутом кадре, max и отдельном compile span. Предварительные измерения с потерянным первым интервалом и устаревшими ссылками после OIT toggle исключены из итоговых чисел.

## Границы результата

Это адресное устранение серии sync rebuild и подтверждённой EMPTY-гонки. Средний FPS всей игры, TPS/AI, все GPU и драйверы не проверены этим сценарием. Собственные постэффекты выключены в количественном fixture для воспроизводимости; native OIT работает в двух режимах. Shader passes, форматы, Pipeline Guard, движение, календарь и серверная authority не изменяются.

DV-011 (частичная геометрия), DV-006 (общая нагрузка очередей) и остальные источники задержек остаются отдельными направлениями. Первая задача сливается только в develop/dv-fixes; main остаётся на предыдущем состоянии до завершения всей программы.
