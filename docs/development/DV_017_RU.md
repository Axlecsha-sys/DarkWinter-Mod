# DV-017: фоновая пересборка изменённых секций

## Текущий маршрут

`LevelRenderer.compileSections` передаёт все подготовленные регионы в штатный `compileAsync`, включая `NEARBY` и `PLAYER_AFFECTED`. Полная сборка одной сложной секции больше не выполняется синхронно в этом месте render thread. Сохраняются owner-thread extraction, бюджет снимков DV-011, native очередь по расстоянию, buffer pool, cancellation, generation guards, staging/upload и visibility. Отдельный приоритет игрока в native `compileAsync` отсутствует; это не новая очередь.

Предыдущий мягкий бюджет гарантировал одну синхронную пересборку даже в опоздавшем кадре. Лимит 2 мс ограничивал только допуск следующих секций: один вызов `SectionCompiler.compile` мог занять намного больше. Поэтому этот путь оставлял источник скачков при разрушении блоков в сложном окружении.

`-Ddarkwinter.sectionRebuildWorker=false` возвращает точный прежний маршрут для изолированного контроля: новые непривилегированные секции идут фоном, остальные используют `SectionCompileBudget`. По умолчанию свойство равно `true`; оно читается при загрузке `LevelRenderer`.

Готовый старый mesh сохраняется до публикации нового. Слишком частые изменения могут отменять незавершённые задачи; задержка от действия до публикации и завершение серии проверяются отдельно. Жёсткий предел времени всего кадра не обещается.

Синхронное журналирование native EDIT-операций на Server thread остаётся отдельным направлением: durable WAL не ослаблен и не перенесён без протокола подтверждения. Новая параллельная стадия BLOCK/SKY по умолчанию выключена и не используется как объяснение клиентских задержек без измерений.

## Отмена пустого результата

При проверке жизненного цикла воспроизведена отдельная ошибка исходной 26.3: EMPTY-ветка CompileTask.doTask публикует результат без повторной проверки отмены. Старый worker может затереть новый готовый mesh и освободить его GPU allocations.

CancelledEmptySectionMixin сериализует cancel и проверку с EMPTY-публикацией одним monitor конкретной задачи. Monitor освобождается до native copyLock и освобождения буферов; ни meshing, ни ожидание GPU под ним не выполняются. При отмене native cleanup получает безопасный EMPTY sentinel вместо нового живого mesh, а результат задачи становится CANCELLED.

Это защита EMPTY и block-entity-only ветки без rendered layers. Она не объявляется универсальной защитой всех nonempty upload callbacks. Остальные вопросы инкрементальных meshes и их версий остаются в DV-011.

- Чистая публикационная сборка проверяется без private tools/tests.

## Измерения тяжёлой серии

Windows, Ryzen 5 8400F, Radeon RX 7600 XT, Java 25; обычный загруженный мир, 1280×720, render distance 8, FOV 110, VSync OFF, framerate setting 260 (unlimited). Симуляция заморожена. Восемь чередующихся before/after bursts содержат по девять готовых непустых секций.

Before отменяет только budget decision в private test mod и воспроизводит исходный неограниченный sync выбор. EMPTY guard включён в обоих финальных timing-вариантах; его исходный repro сохранён отдельно. Production не содержит тестовых flags.

После правки весь mesh в этой сцене наблюдается готовым примерно через 49–50 мс от mark против 76–95 мс до неё. Проверка готовности выполняется SDK с дискретностью примерно 20 Hz; это верхняя граница первого наблюдения, не точный аппаратный момент публикации.

Сохранены все frame intervals, p50/p95/p99/max и реальные sync/async spans. В короткой фазе единственный hitch может составлять меньше 1% кадров, поэтому p99 не всегда включает его; итоговый вывод основан также на первом затронутом кадре, max и отдельном compile span. Предварительные измерения с потерянным первым интервалом и устаревшими ссылками после OIT toggle исключены из итоговых чисел.

## Границы результата

Это адресное устранение серии sync rebuild и подтверждённой EMPTY-гонки. Средний FPS всей игры, TPS/AI, все GPU и драйверы не проверены этим сценарием. Собственные постэффекты выключены в количественном fixture для воспроизводимости; native OIT работает в двух режимах. Shader passes, форматы, Pipeline Guard, движение, календарь и серверная authority не изменяются.

DV-011 (частичная геометрия), DV-006 (общая нагрузка очередей) и остальные источники задержек остаются отдельными направлениями. Первая задача сливается только в develop/dv-fixes; main остаётся на предыдущем состоянии до завершения всей программы.
