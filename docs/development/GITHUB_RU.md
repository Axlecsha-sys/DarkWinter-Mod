# Публикация исходников

Рабочий проект — `F:\DarkWinter`. Публикую чистую копию `build/github-ready-20261031-compact` в ветку `main` репозитория [DarkWinter-Mod](https://github.com/Axlecsha-sys/DarkWinter-Mod). Локальная история, игровые данные и готовые сборки в исходники не входят.

## Состав

Публикуются исходники мода и Visuals-модуля, ресурсы, исходники лаунчера, Gradle wrapper, конфигурация обычной сборки, актуальная документация и обязательные лицензии.

Каталоги с именами `tools` и `tests` исключены через [.gitignore](../../.gitignore). В них остаются локальные Lab, проверки, генераторы ресурсов и средства обслуживания сервисов. Если локальные каталоги доступны, Gradle подключает их дополнительные задачи. Обычная сборка опубликованного проекта от них не зависит.

Контракт Visuals, обязательный для сборки, находится в `modules/darkwinter-visuals/config/pipeline_contract.json`. Старые отчёты, промпты и промежуточные материалы сохранены локально внутри исключённой `.darkwinter-lab/docs-archive-20261031/`.

## Перед отправкой

1. Собирать и проверять именно чистый снимок, в котором нет `tools/tests`.
2. Проверить отсутствие профилей, миров, журналов, ключей, резервных копий и готовых бинарных сборок в индексе.
3. Сохранять историю ветки `main`, не перенося в неё старую локальную историю с резервными копиями.
4. Синхронизировать публикационную копию с рабочим проектом, создать коммит и выполнить push в `main`.

В полном рабочем проекте проверка обычной сборки без локальных инструментов запускается так:

```powershell
.\gradlew.bat verifyPublicationBuild
```

Задача заново создаёт собственную копию входов сборки в `build/publication-check/source`, исключает `tools/tests` и предыдущие результаты, затем выполняет `build wkeVerifyPackage`. Компилятор и заголовки подготавливаются самой сборкой этой копии. Публикационный Git-каталог `build/github-ready-20261031-compact` задача не изменяет. Успех этой проверки подтверждает собираемость входов; аудит файлов и будущего публичного индекса остаётся отдельным обязательным этапом.

Обычная сборка описана в [руководстве разработчика](BUILD_RU.md). Локальные инструменты аудита и экспорта не входят в публикацию.


## Уведомления о разработке в Telegram

Файл `.github/workflows/telegram-notify.yml` отправляет сообщения в `@winterkore` через `@DarkWinterGitBot`.
Необходимо настроить GitHub Actions Secret `TELEGRAM_BOT_TOKEN`, токен в репозиторий не добавлять.

- Каждые 5 минут (время запуска зависит от GitHub Actions) workflow в основной ветке проверяет **все** ветки через GitHub API — даже старые ветки, где самого workflow нет. Push в `main` также запускает внеплановую проверку.
- Первый проход только запоминает текущие SHA веток и не публикует старую историю. Состояние хранится в кэше GitHub Actions. При очистке/истечении срока кэша может потребоваться новая начальная фиксация состояния.
- Новые коммиты публикуются по одному. Ранее отправленные SHA запоминаются, чтобы не публиковать их повторно при обычном переносе между ветками.
- Слияния через Pull Request (Merge, Squash, Rebase) публикуются событием `pull_request_target.closed`, если `merged == true`. Прямые merge-коммиты определяются по наличию нескольких родителей; синхронизация fast-forward определяется в пределах наблюдаемых SHA веток, но не все прямые fast-forward операции можно однозначно распознать.
- Issues: создание, изменение, закрытие, повторное открытие; комментарии Issues: создание и редактирование. Комментарии под Pull Requests сюда не относятся.
- Новые опубликованные релизы с текстом и ссылками на файлы также отправляются в Telegram.
- Формат сообщений без добавленных декоративных эмодзи. Ненадёжный текст GitHub экранируется для Telegram HTML.
- Ручная проверка: GitHub → Actions → DarkWinter Telegram notifications → Run workflow → `test` (отправить тест в канал) или `scan` (проверить все ветки).
- Перед отправкой публикации workflow проверяет синтаксис скрипта и запускает автономные unit-тесты без обращений к Telegram.
- Гарантии мгновенной доставки нет: расписание GitHub может задерживаться; события и ранее закрытые ветки в период простоя могут быть недоступны. Секрет не логируется намеренно.
