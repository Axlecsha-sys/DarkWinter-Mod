# DV-032: задержки панели F10

## Причина и изменение

F10 переключает диагностику тестового острова в TestingClient. Это отдельный интерфейс от записи /dwperf. В исходной реализации sampleDiagnostics раз в секунду вызывал OperatingSystemMXBean.getProcessCpuLoad на render thread, а pollErrorLog раз в две секунды синхронно открывал и разбирал последние 64 KiB latest.log.

На Windows 11 / Java 25.0.4.1 / Ryzen 5 8400F вызов getProcessCpuLoad в отдельной JVM занимал в среднем 42,87 мс при частоте 1 Hz, максимум 51,07 мс. Самый первый вызов — 687,26 мс. Это стоимость API на этой машине, а не атрибуция конкретного ранее записанного кадра.

TestingDiagnosticSampler переносит CPU-счётчик и ограниченное чтение журнала в один ленивый daemon worker. Одновременно существует не более одной задачи. Запрос с клиентского потока возвращает готовый неизменяемый снимок без ожидания. Результаты принадлежат поколению текущей диагностической сессии; F10 OFF и смена мира инвалидируют старое поколение, сохраняя занятый слот до завершения worker. Завершение клиента закрывает sampler без ожидания native CPU-вызова.

Кольцо из 120 интервалов и график обновляются каждый кадр. Текст панели и статистика кольца пересчитываются раз в 200 мс. Состав панели и расположение редактора справа сохраняются.

## Проверка

Детерминированные проверки: 1035 assertions по расписанию 1 s / 2 s, ограничению очереди, заблокированному worker, переключениям мира/F10, устаревшим результатам, закрытию, отказу executor, отдельным ошибкам CPU/журнала и реальному ограничению хвоста 64 KiB / 32 строки / 512 символов. Core DV-032: 220 assertions.

Native Loom / OpenGL / RX 7600 XT: по три пары F10 OFF/ON, по 10 секунд на фазу в каждой версии. Использованы копии одного сохранения, фиксированные камера и viewport 1280×720, одинаковый block-state scene hash, обычные серверные тики без SDK scheduling. Production collector и JFR включены в обеих версиях.

До изменения все 30 CPU-вызовов полностью находятся внутри 30 отдельных медленных кадров; ни один вызов не пересекается с GC-паузой. Средняя стоимость вызова — 47,001 мс, диапазон 43,471–56,974 мс. JFR фиксирует стек getProcessCpuLoad0 → getProcessCpuLoad → TestingClient на Render thread.

После изменения JFR фиксирует эти вызовы только на DarkWinter diagnostic sampler. Их стоимость достигает 94,040 мс, но игровой поток их не ожидает. Единственный оставшийся measured ON-скачок 26,564 мс не пересекается с worker CPU или GC; его причина не установлена. В OFF-контроле зарегистрированы 3 и 5 длинных кадров соответственно.

Первое включение учитывается отдельно от steady phases: до исправления CPU-вызов 183,265 мс расположен внутри кадра 260,595 мс. После исправления первый CPU-вызов выполнялся 200,216 мс в фоне; при этом остался кадр 80,284 мс с неизвестной причиной. Полное устранение всех задержек при первом открытии не заявляется.

Последняя исходная ON-фаза имеет configChanged, поэтому общего FPS/TPS-выигрыша по этим прогонам не заявляется. Методные интервалы и JFR устанавливают конкретную периодическую блокировку независимо от такого сравнения. Все AFTER-фазы прошли без изменения конфигурации, переполнения и непродвинувшихся тиков.

## Ручная запись 01c621dc

JSON schema 1 длительностью 30,033 s содержит 3761 интервал кадра, 600 серверных тиков и 471 GPU-измерение. Статистика исходных массивов согласуется с отчётом: средний интервал 7,970 мс, p99 9,778 мс, максимум 214,843 мс; серверный максимум 110,152 мс; максимум очереди секций 36.

Общих временных меток frame/render/tick/queue в этой схеме нет. Позиции максимумов различаются, поэтому считать их одним событием нельзя. У кадрового максимума соседние значения очереди равны нулю, но это не устанавливает причину. GPU измерен только на каждом восьмом render scope и не включает present/compositor. Накопленное collectionTime не является временем отдельных STW-пауз.

sceneHash=unverified, sceneChanged/configChanged и tpsComparable=false запрещают использовать эту ручную запись как строгое A/B-доказательство ускорения. Исходные задержки 214,843 и 110,152 мс остаются неатрибутированными. Для следующего их воспроизведения нужны общая временная шкала и JFR; исправление F10 их задним числом не объясняет.
