# DV-018: временные объекты при обновлении сцены

Первый адресный этап уменьшает выделения памяти в TestingScene.sync. Весь движок Minecraft и все источники временных объектов этим изменением не перерабатываются.

## Подтверждённый источник

Сцена обновляется каждые 20 серверных тиков. Прежняя цепочка origins.entrySet().stream().filter(...).map(...).sorted().toList() посещала каждую запись происхождения, включая природные категории, которые затем отбрасывались.

На установленном JDK 25 EntrySpliterator ConcurrentHashMap создаёт MapEntry при обходе, а read-only view добавляет UnmodifiableEntry. Это подтверждено не только исходниками JDK: native JFR содержит оба класса со стеком через настоящую TestingScene.sync. JFR-события и веса используются для определения места выделения, а не для подсчёта всех объектов.

## Изменение

Позиции building/object собираются через последовательный Map.forEach прямо из существующих key/value. Затем локальный ArrayList сортируется тем же естественным порядком Long. Обёртки записей для отбрасываемых природных origins больше не нужны. Полный обход origins остаётся O(N); индексация категорий и кеш всей сцены не добавляются.

Проверки загруженности, AIR, принадлежности, footprint, native NBT, создание идентификаторов и дальнейшая обработка сохранены. Изменён только способ перечисления кандидатов внутри sync. Read-only view происхождения продолжает запрещать обход учёта изменений из DV-008.

## Native before/after

Minecraft 26.3 / Fabric / Java 25, OpenGL на RX 7600 XT. Две копии одного flat save, 100 000 terrain origins, без массовой правки блоков. Модули и F10 выключены, камера фиксирована. Пять секунд прогрева, затем по 12 настоящих периодических sync на Server thread. Сервер продолжает native ticks без SDK/GameTest scheduling hooks.

ThreadMXBean снимается на границах настоящего метода; создание JFR-события и экспорт отчёта исключены из измеренной разницы. JDK определяет этот счётчик как приблизительный: это наблюдаемый delta выделений потока, не физическая занятость heap и не точное количество объектов. JVM flags и настройка GC не меняются, явный GC не вызывается.

| Наблюдение | До | После |
| --- | ---: | ---: |
| Измеренные sync | 12 | 12 |
| Разница счётчика на каждый вызов | 4 002 928 B | 2 392 B |
| Суммарная разница за 12 вызовов | 48 035 136 B | 28 704 B |
| Среднее wall time метода | 1,236 мс | 0,608 мс |

В исходной JFR зарегистрированы MapEntry и UnmodifiableEntry со стеком через sync; в исправленной записи таких sampled allocation sites внутри sync не зарегистрировано. Это не означает нулевых выделений: счётчик сохраняет 2 392 B на вызов.

В этом сценарии разница счётчика уменьшилась примерно на 99,94%. Все 12 значений каждой версии совпали между собой. Logical SHA-256 origins одинаков до/после и между версиями, scene.json остаётся отсутствующим, views — пустыми; native ticks и gameTime продвигаются. Сравнивается конкретный метод в сцене без авторских объектов, а не общий FPS/TPS или распределение GC-пауз. Один before/after прогон не доказывает статистически значимый общий выигрыш игры.

## Проверки поведения

После профилирования настоящий редактор отдельно прошёл четыре группы native-проверок:

- порядок создания по signed packed Long на отрицательных и положительных координатах; игнорирование terrain, отсутствующей категории, AIR и выгруженных крайних координат без загрузки новых чанков;
- замена категории, удаление и повторное обнаружение объекта; сохранение ID остальных узлов и порядка уже существующих;
- именованная группа с точным составом, переименование, сохранение parent IDs и выбранной группы после повторных sync;
- настоящий batch контейнера с 13 алмазами и 9 изумрудами, Undo/Redo с точным типизированным NBT, ID сундука и полным восстановлением scene.json.

Проверки используют actual TestingScene и штатные транзакции; отдельной копии перечисляющего алгоритма в тестах нет. Functional-контроль baseline явно NOT_RUN, эти проверки выполнены на исправленной версии после остановки профиля.
