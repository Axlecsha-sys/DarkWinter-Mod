# Эксперимент: реальная пакетная запись геометрии Minecraft 26.3

## Область выполненной работы

В ветке `develop/с++` добавлен отдельный клиентский эксперимент `/dwmesh`. Это перенос **финальной записи готовых граней в штатные вершинные буферы**, а не полная замена `SectionCompiler`, генератора мира или графического движка.

Java/Fabric по-прежнему выбирает модели, выполняет отсечение, трансформации, tint, AO и свет. Новый адаптер получает окончательные данные граней, группирует их и записывает в исходный `BufferBuilder`. Графические команды, загрузка на GPU, OpenGL/Vulkan, шейдеры, сортировка прозрачности и серверные игровые правила не заменялись. Никаких новых погодных или иных механик DarkWinter не добавлено.

Работают три режима: `VANILLA` (обычный Minecraft/Fabric с диагностическими перехватами), `JAVA_PACKED` (те же пакеты обрабатывает Java), `CPP_PACKED` (пакеты обрабатывает собственная C++ DLL). По умолчанию VANILLA. Старый эксперимент `/dwvoxel` с дополнительным 18³ обходом блоков отключается при выборе режима `/dwmesh` или запуске сравнения: он не нужен новому пути.

## Что именно обрабатывается

Поддержаны финальные слои `SOLID` и `CUTOUT` с проверенным форматом `DefaultVertexFormat.BLOCK`, 28 байт на вершину. Слои имеют отдельные накопители: чередование камня и листвы не вызывает сброс чужого буфера. Максимум 1024 грани в пакете, два накопителя на контекст, ограниченный пул повторного использования на рабочем потоке. Маленькие остатки менее 32 граней записывает Java и в режиме CPP_PACKED.

Обычный путь Minecraft использует шаблоны `BakedQuad` и окончательные цвета/свет `QuadInstance`. Путь Fabric Indigo берёт 32 уже вычисленных слова вершины из `QuadViewImpl.buffer(int, VertexConsumer)` и сразу копирует их, прежде чем изменяемый emitter будет использован повторно. Ссылки на изменяемые emitter/массив не хранятся. Для Indigo геометрические координаты и UV переносятся бит-в-бит без повторной арифметики.

C++ пишет непосредственно в участок памяти, который зарезервировал оригинальный `ByteBufferBuilder`. После следующего reserve адрес может стать недействительным, поэтому он используется только в синхронном вызове и не сохраняется. Входные пакеты перед вызовом копируются в ограниченные нативные scratch-буферы; обратной копии выходных вершин нет. Java-вариант Indigo упаковывает слова в переиспользуемый массив и применяет одну bulk-copy вместо отдельных FFM-записей каждого атрибута.

Порядок граней внутри каждого буфера не меняется. Перед штатной записью в буфер с отложенным пакетом установлен flush-барьер; дополнительный барьер сохранён перед жидкостями. `TRANSLUCENT`, жидкости, неподходящие форматы и неожиданные дополнительные буферы сохраняют оригинальный путь. Это не алгоритм объединения соседних граней и не упрощение моделей.

## Запуск

Из `F:\DarkWinter` при закрытом клиенте:

```powershell
.\gradlew.bat blockMeshVerify
.\gradlew.bat runClient
```

Первой командой собирается та же DLL `build/voxel-faces/bin/dw_voxel_faces.dll` через уже установленный переносимый Zig/Clang. Обычная задача `build` не зависит от C++-компилятора; DLL и standalone-тесты не упаковываются в игровой JAR. Клиентские адаптеры входят в JAR, но выключены по умолчанию. При отсутствии DLL, нужного native access или подходящего ABI сохраняется VANILLA.

В мире доступны:

```text
/dwmesh status
/dwmesh mode vanilla
/dwmesh mode java
/dwmesh mode cpp
/dwmesh rebuild
/dwmesh compare 4
```

`mode` применяется к последующим сборкам секций. `rebuild` запрашивает штатную полную пересборку видимых секций. Настройка хранится в `run/config/darkwinter/mesh-experiment.properties`. Старый режим хранится отдельно в `voxel-experiment.properties` и для этого эксперимента должен оставаться JAVA.

## Сравнение на реальных секциях

`/dwmesh compare 4` автоматически выбирает VANILLA, ожидает закрытия чата и запрашивает пересборку. На подходящем рабочем потоке тот же объект `RenderSectionRegion` последовательно обрабатывается всеми тремя режимами. Снимок не передаётся другому потоку и не перечитывается из меняющегося мира для каждого варианта. Отдельные результаты освобождаются, основной игровой результат не подменяется.

Для каждой выбранной секции сначала проверяется повторяемость штатного пути, затем выполняются две прогревочные ротации и пять измерений на режим с изменяющимся порядком. Сравниваются полностью вершинные и индексные байты всех слоёв, draw-state и список блок-сущностей. В отчёте есть SHA-256 эталонных буферов, сырые измерения, медианы, `byteParity`, `nativeExercised`, число настоящих native-вызовов и ошибок fallback. Пустой или неиспользовавший C++ прогон не должен выдаваться за проверенную нативную работу.

JSON записывается в `run/performance-reports/chunk-mesh-<UUID>.json`. Это **не FPS-бенчмарк**: диагностическая команда намеренно повторяет CPU-работу. `wallNanos` — время вызова полной сборки секции, включающее подготовку пакетов, reserve, перенос входа, запись и FFM; это не чистое процессорное время потока. Проверка/хеширование готовых буферов, GPU upload и начальное создание тестового buffer pack находятся вне этого интервала. Подробные component clocks выключены по умолчанию, чтобы не измерять каждую грань в обычном пути. Их включает startup property `-Ddarkwinter.mesh.detailedTiming=true`: тогда отдельно измеряются подготовка пакета, reserve, запись, входная копия и native call. Без этого флага компоненты равны `-1/UNAVAILABLE`, а полное wall time компиляции сохраняется. Флаг включён в metadata/configHash и отчёт сравнения; записи с разной детализацией не следует смешивать как одинаковую конфигурацию.

При обычной записи DV-032 режимы добавлены в metadata/configHash как `chunkMeshMode` и `chunkMeshEffective`. Для оценки FPS нужны отдельные одинаковые маршруты и достаточные повторы, без `/dwmesh compare` одновременно.

## Проверки и честные ограничения

`blockMeshVerify` проверяет 640 разнообразных и параллельных пакетов: 384 шаблонных и 256 Indigo, независимый byte-oracle, охранные байты до/после невыровненного выхода, NULL, ошибочные размеры/индексы, ограничение объёма и конкурентные вызовы. `voxelFacesVerify` дополнительно сохраняет 264 проверки старого алгоритма масок.

Первый игровой перехват штатных lambda-выводов не охватил подмену Fabric Indigo. Его отчёт с нулём образцов и timeout сохранён как неуспешный, после чего добавлен перехват настоящего `QuadViewImpl.buffer`. Последующие игровые сравнения дали побайтовое совпадение реальных геометрических буферов и подтвердили фактическое выполнение native-кода. История промежуточных отчётов сохранена; она не означает гарантированного прироста FPS.

Реально проверенная платформа — Windows x64, Java 25, Fabric 26.3 и установленный Indigo. Совместимость нового пути с Linux/macOS, другим рендерером, иными версиями Fabric, всеми ресурс-паками и выделенным сервером не подтверждалась. Финальные численные результаты и пути журналов приведены в отчёте DarkWinter Lab этой работы. Малое число секций и прогревов не доказывает статистически устойчивый выигрыш. Штатный режим в этой ветке содержит диагностические перехваты, поэтому это не отдельный незатронутый vanilla-бинарник.

Java fallback обрабатывает недоступность библиотеки и обнаруженные ошибки вызова; он **не гарантирует восстановление после повреждения памяти или аварии нативного процесса**. Библиотека не выгружается, пока её могут использовать рабочие потоки. По результатам эксперимента VANILLA оставляется безопасным режимом по умолчанию.

## Остальные направления из плана

Математика генерации мира, seed/float-совместимость, распространение света, серверное хранение чанков, видимость на кадре, AI и поиск пути в этой работе не переносились. Они остаются отдельными этапами после профиля соответствующих горячих функций. Быстрая запись вершин сама по себе не доказывает ускорения генерации, загрузки чанков или всей игры.
