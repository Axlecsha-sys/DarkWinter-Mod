# DarkWinter Core — этап 1

Дата: 06.11.2026. Платформа проверки: Windows x64, C++20 (Zig/Clang 0.14.1), Java 25 для временного адаптера.

## Принятое направление

- Сначала новое ядро работает рядом с Minecraft 26.3/Fabric, затем получает самостоятельный запуск.
- Первая цель — одиночная игра; кооп подключается позже отдельным слоем.
- Существующие миры импортируются в собственный формат через копии.
- Производительность и качество изображения важнее совместимости с готовыми модами Fabric.
- Обязательная поддержка JVM для будущей самостоятельной игры не вводится.

## Что работает сейчас

`native/darkwinter-core` — самостоятельная C++-библиотека, консольная программа и проверки. В нативном модуле нет Minecraft, Fabric, JNI или ссылок на Java-объекты. Он выполняется без JVM и сборщика мусора Java. Стандартные C++-контейнеры и shared_ptr используют явное время жизни, выделение и освобождение памяти; это не обещание отсутствия любых задержек аллокатора.

- Неизменяемые снимки участков 16×16×16 с идентификаторами состояний блоков.
- Строго возрастающие ревизии; старое задание не может опубликовать результат поверх новой ревизии.
- Собственный пул C++-потоков, ограниченные очереди и число удерживаемых билетов.
- Зависимость задания от одного ранее созданного задания, распространение ошибки зависимости, отмена и явное освобождение результата. Это ограниченный граф v1, без общего join нескольких зависимостей.
- Публикация и отмена согласованы одним протоколом; функции публикации не должны повторно входить в планировщик.
- Пять уровней занятости участка: 16³, 8³, 4³, 2³ и корень. Всего 586 байт битовых данных.
- Собственный формат DWV v1 и проверка целостности до замены состояния.
- Автономные CLI-проверка и измерение на одном и нескольких рабочих потоках.
- Java 25 FFM-адаптер, самостоятельный импортёр Anvil и явная диагностическая команда Fabric `/dwcore inspect <файл.dwv>`.

Занятость означает наличие не-воздушного состояния, а не сплошную коллизию. Вода, растения, ступеньки и мебель требуют своей геометрии на следующем этапе. Нынешняя иерархия пригодна для грубого пропуска пустых областей; это ещё не воксельный рендерер.

## Владение и границы

Снимки принадлежат C++; входные 4096 идентификаторов копируются в одном синхронном вызове. Указатели на Java-массивы или временные FFM-сегменты нативная часть не сохраняет. Асинхронные задания держат C++-снимок; destroy отменяет оставшуюся работу и присоединяет потоки до освобождения ядра. Вызовы не должны пересекаться с destroy того же C-дескриптора. Билеты заданий действуют только внутри создавшего их ядра.

Пределы v1: 1–32 рабочих потока, очередь 1–4096, максимум 4096 участков, 65536 идентификаторов материалов, до 8 МиБ имён материалов и до 256 МиБ входного DWV. Завершённые билеты тоже ограничены и требуют release. Показатели памяти — логические размеры принадлежащих ядру структур, не полный RSS/commit процесса.

Нормальная игра только регистрирует команду. Нативная библиотека и её рабочие потоки загружаются при явной проверке. Существующие симуляция, встроенный сервер и рендер Minecraft продолжают работать.

## Формат DWV v1

Все числовые поля little-endian.

| Область | Состав |
| --- | --- |
| Заголовок, 40 байт | DWVOXEL + нулевой байт; версия u32; сторона u32; число материалов u32; число участков u32; размер полезных данных u64; FNV-1a64 полезных данных |
| Материал | id u32; flags u32; длина имени UTF-8 u32; имя и канонические свойства |
| Участок | x/y/z как три i32; ревизия u64; 4096 идентификаторов u32 |
| Индексация ячейки | x + 16*z + 256*y |

Материал 0 — minecraft:air. Дополнительный AIR-флаг сохраняет различие cave_air/void_air без ложной занятости. Импортёр нормализует порядок свойств и назначает детерминированные идентификаторы.

Сохранение создаёт новый файл: сначала полностью пишет временный файл, затем публикует его эксклюзивной жёсткой ссылкой в том же файловом разделе. Существующий файл не заменяется. Файловая система без поддержки жёстких ссылок получает явный отказ. Гарантия сохранности при аварийном отключении питания пока не реализована.

## Импорт и проверенная локация

Проверена копия готовой дорожной SDK-локации из build/run. Исходные регионы проверены SHA-256 до и после копирования; импортёр читает только новую копию и повторно проверяет её после импорта.

Поддержаны расположение регионов 26.3 внутри dimensions/minecraft/overworld/region и старое расположение region; компрессия GZip, Zlib и None, внешние MCC. Другие способы компрессии отвергаются. Поддержаны палитры 26.3 из строк, id/properties и обёрток смешанного NBT-списка, а также старые Name/Properties. Чтение ограничено по размеру, глубине и числу NBT-узлов.

На проверенной локации: **60 участков, 245760 ячеек, 3258 не-воздушных ячеек, 807 ячеек DarkWinter и 22 состояния**. Сохранены, в частности, ось, расстояние и индекс проводов, направление и части столбов/ограждений. SHA-256 DWV: `3534d5da68250a16173fe1a39891e7e56b07a8fb2b55f4b5b236d3d714eb4e10`.

Это импорт сериализованных состояний выбранного объёма. Пропущенные кодеком значения свойств по умолчанию пока не раскрываются из реестров Minecraft; связывание с полным каталогом форм и материалов относится к следующему этапу. Сущности, block entities, биомы, свет, содержимое контейнеров, инвентари и игровое состояние ещё не переносятся. Это не полная миграция игрового сохранения.

## Проверки

- Нативный стенд: 306547 assertions, независимый побитовый oracle и одинаковый результат 1/4 потоков, реальные перекрывающиеся рабочие потоки, отмена, зависимости, ограничение очереди, устаревшие ревизии, повреждение файла, детерминированное сохранение и запрет перезаписи.
- Автономный `dw_core_tool.exe inspect` успешно прочитал тот же DWV в окружении с одним Windows System32 в PATH, без JAVA_HOME и JDK. В таблице импортов EXE нет JVM/Java-библиотек.
- FFM: 179 проверок на импортированной локации, 1/4 потока, сохранность массива состояний, физическая длина входа, границы отмены, 20 циклов создания/закрытия и палитры 26.3.
- Клиентская проверка: отдельная задача coreVerifyClient проходит через настоящую команду Fabric и сверяет подготовленные данные с точным импортированным файлом. Результат задачи и её JSON являются источником статуса, а не наличие команды в коде.
- Обычная Java-сборка и visualsDoctor проверяют подключение адаптера без изменения графической цепочки.

Промежуточные неуспешные запуски сохранены в журналах Lab. Исправлены выбор каталога измерения, варианты кодека палитры и ожидание обоих независимых заданий в тесте отмены.

## Запуск

Из корня проекта с JDK 25 и уже установленным проверенным Zig 0.14.1:

~~~powershell
.\gradlew.bat coreStage1Verify
.\gradlew.bat coreVerifyClient
.\gradlew.bat build
~~~

Обычная build не требует C++-компилятора и не собирает DLL. Автоматического скачивания toolchain здесь нет. CMake-файл подготовлен для других платформ; исполнение вне Windows x64 пока не проверялось.

Для собственной закрытой копии в build/run:

~~~powershell
.\gradlew.bat coreStage1Verify -PcoreSourceWorld="build/run/my-copy"
~~~

Без свойства выбирается последняя доступная дорожная SDK-локация. Результаты и копия находятся в build/core/runs; build/core/latest-stage1.json указывает завершённый общий прогон. Подготовленные файлы экспортируются в build/core/exports. Бинарники — build/core/bin/dw_core.dll, dw_core_tool.exe, dw_core_checks.exe.

При разработческом runClient библиотека и каталог экспортов передаются через свойства запуска. Команда /dwcore inspect <имя.dwv> выполняет диагностику в фоне и освобождает созданное ядро. Библиотека остаётся загруженной до завершения JVM; отключать её из-под работающих потоков нельзя.
